# Архитектура

Документ описывает решение по мере его проектирования. Постановка задачи: [TASK.md](../TASK.md).

## Стек

| Назначение | Выбор |
|---|---|
| Парсинг HTML | BeautifulSoup (`beautifulsoup4`) |
| HTTP-клиент | `requests` (синхронный) |
| Хранилище | SQLite |
| Доступ к БД | SQLAlchemy 2.0 (ORM, синхронный) |
| Схемы API и настройки | Pydantic, pydantic-settings |
| Резюме отзывов | LLM через OpenAI-совместимый API (`/v1/chat/completions`, `requests`); по умолчанию `claude-haiku-5-5` |
| Миграции БД | Alembic |
| Бэкенд и веб-интерфейс | FastAPI + uvicorn (один процесс) |
| Веб-интерфейс | React, TypeScript, Vite, Tailwind CSS, shadcn/ui, TanStack Query |
| Планировщик | APScheduler 3.x (`AsyncIOScheduler`), версия закрепляется как `>=3.10,<4` |

## Общая схема

```
Metacritic ──► Парсер списка игр ──► ссылки на игры
                                          │
                                          ▼
                              Парсер страницы игры ──► SQLite
                                                          ▲
                              Обработка отзывов (позже) ──┘
```

## Структура проекта

Репозиторий делится на две независимые части:

```
metacritic_dashboard/
├── backend/
│   ├── app/
│   │   ├── sources/        # источники данных (граница с внешним миром)
│   │   │   ├── base.py         # интерфейс GameSource и общие модели
│   │   │   └── metacritic/     # HTTP-клиент, парсеры, MetacriticSource
│   │   ├── db/             # модели SQLAlchemy, сессии, репозиторий
│   │   ├── services/       # бизнес-логика: цикл синхронизации и т.д.
│   │   ├── api/            # роутеры FastAPI и Pydantic-схемы
│   │   ├── scheduler.py    # APScheduler
│   │   ├── config.py
│   │   └── main.py         # приложение FastAPI, lifespan
│   ├── tests/
│   ├── pyproject.toml
│   └── .env.example
├── frontend/    # веб-интерфейс (UI)
├── docs/
├── AGENTS.md
├── CHANGELOG.md
└── TASK.md
```

Принцип: абстракция вводится только там, где ожидается замена, то есть на границе с источником данных (сегодня Metacritic, позже, например, Steam). FastAPI, SQLAlchemy и Pydantic используются напрямую, без обёрток.

Фронтенд общается с бэкендом только через HTTP API. Зависимости, конфигурация и тесты бэкенда лежат внутри `backend/`.

## Источники данных

Всё, что относится к конкретному сайту, изолировано в `app/sources/<имя>/`. Остальной код работает только с интерфейсом `GameSource` и общими моделями из `sources/base.py` (`Game`, `PlatformScore`).

```python
class GameSource(Protocol):
    name: str                                    # "metacritic", позже "steam"
    def discover(self, limit: int) -> list[str]: ...              # самые новые игры, новые сверху
    def fetch_game(self, ref: str) -> Game: ...
    def fetch_reviews(self, game: Game, kinds) -> ReviewBundle: ...  # отзывы для резюме
```

- `discover` возвращает идентификаторы (`ref`) самых новых игр источника, новые сверху; `limit` — сколько игр просмотреть. Список нужен только чтобы **найти** новые игры, обновляются игры по собственным ссылкам (`fetch_game(ref)`).
- `fetch_game` загружает и разбирает одну игру целиком, включая все дополнительные запросы (для Metacritic это Userscore по каждой платформе).
- Новый источник добавляется реализацией `GameSource` и регистрацией в `main.py`, остальной код не меняется.
- `fetch_reviews` собирает отзывы критиков и пользователей из доступных источников (см. «Шаг 3») и возвращает `ReviewBundle`: список отзывов и сводную статистику. Параметр `kinds` ограничивает, отзывы каких типов загружать.
- Игра в БД идентифицируется парой `(source, slug)`.

## Запуск по расписанию

В сервисе два независимых конвейера, у каждого своё расписание, свой лимит и своя блокировка:

| | **Обход** (`crawl`) | **Анализ** (`analysis`) |
|---|---|---|
| Что делает | просматривает списки, загружает страницы игр (новые и повторные визиты), пишет в БД игры, оценки и общие оценки | берёт игры из БД, загружает их отзывы, строит резюме ИИ |
| Расписание | раз в час (`CRAWL_INTERVAL_HOURS`), первый запуск сразу при старте (`SYNC_RUN_ON_STARTUP`) | раз в час (`ANALYSIS_INTERVAL_HOURS`), первый запуск через 30 минут после старта (`ANALYSIS_OFFSET_MINUTES`), так что он идёт на полчаса позже обхода и не конкурирует с ним за сайт |
| Лимит за запуск | 250 игр (`CRAWL_BUDGET`) | 40 игр (`ANALYSIS_BUDGET`) |
| Модель | не использует | использует; без `LLM_API_KEY` конвейер выключен |

Конвейеры могут работать одновременно; каждый ходит на сайт через свой экземпляр источника с собственной паузой между запросами.

- `AsyncIOScheduler` создаётся и запускается в `lifespan` FastAPI и останавливается при завершении приложения; в нём две задачи с `max_instances=1`: новый запуск конвейера не стартует, пока идёт его предыдущий.
- Парсинг синхронный (`requests` + BeautifulSoup), поэтому задачи вызывают конвейеры через `asyncio.to_thread`, чтобы не блокировать API. Занятость конвейера (`PipelineRunning`) перехватывается, такт пропускается.
- Принудительный запуск (кнопка в интерфейсе) вызывает тот же конвейер; защита от параллельного запуска общая: блокировка конвейера плюс `max_instances=1`.
- Планировщик создаётся функцией `create_scheduler` в `app/scheduler.py`. Приложение собирается фабрикой `create_app(source, scheduler_enabled)`: в тестах подставляются заглушка источника и отключённый планировщик; без заглушки каждому конвейеру создаётся свой `MetacriticSource`.
- Приложение запускается одним процессом uvicorn (без `--workers N`), иначе у каждого воркера появится свой планировщик.

### Обход: открытие и повторные визиты

Список «новые» на Metacritic нестабилен: порядок внутри одной даты меняется, а игры уходят вниз быстро (замер: через 1–3 часа 27 % найденных игр уже вне первых 800 позиций). Поэтому списки служат только для **открытия** новых игр, а обновляются игры по собственной ссылке `/game/<slug>/`, которая от списка не зависит.

- **Открытие.** Каждый запуск `source.discover(DISCOVERY_DEPTH)` возвращает идентификаторы самых новых игр (для Metacritic: сначала New Releases, затем страницы SEE ALL, пока не набрано `DISCOVERY_DEPTH` игр, по умолчанию 250). Игры, которых нет в базе, считаются новыми.
- **Повторные визиты.** У каждой игры в базе есть срок следующей проверки `games.next_check_at`. В работу идут игры, у которых срок наступил, самые просроченные первыми. Игра обновляется целиком: страница игры, оценки по платформам, общие оценки.
- **Расписание повторных визитов.** После обработки срок ставится так: игре моложе `YOUNG_DAYS` (30 дней с момента, когда мы её нашли) — через `REVISIT_YOUNG_HOURS` (24 часа), старше — через `REVISIT_OLD_DAYS` (7 дней). Возраст считается от `first_seen_at`.
- **Лимит и порядок.** За запуск загружается не больше `CRAWL_BUDGET` игр (по умолчанию 250). Порядок простой: сначала новые игры (в порядке списка), затем повторные визиты, самые просроченные первыми. Загрузка страниц ничего не стоит, поэтому места между группами не делятся: лимит нужен только чтобы запуск укладывался в час. Если новых игр когда-нибудь станет больше лимита, повторные визиты подождут следующего запуска.
- **Сбои.** Новая игра, которую не удалось загрузить, в базу не попадает и будет найдена снова при следующем открытии, пока она в первых `DISCOVERY_DEPTH` позициях. Игра из базы, которую не удалось загрузить, откладывается на `REVISIT_YOUNG_HOURS`, чтобы не забивать запросами «битую» страницу.
- **Журнал.** Запуск записывается в `sync_runs` с `pipeline = crawl`: `games_found` — сколько игр выбрано, `batch_index` — порядковый номер успешного запуска этого конвейера за день (справочно). Запись создаётся со статусом `running` до начала работы, её счётчики обновляются после каждой игры (для мониторинга в реальном времени). Статус `success` ставится, когда открытие прошло и выбранные игры обработаны, сбой отдельной игры учитывается в `games_failed`; `failed` — если не удалось получить список или произошла непредвиденная ошибка. Для каждой обработанной игры в `run_games` пишется строка с итогом: `new` (новая игра), `revisited` (обновлена) или `failed` (с текстом ошибки); строки появляются по ходу запуска.

### Обнаружение изменений

Хэш всей HTML-страницы не используется: в ней много динамического шума, а скачивать страницу всё равно приходится. Вместо этого:

- по описательным полям игры (название, обложка, разработчик, описание, видео, жанры; нормализованный отсортированный JSON) считается `games.content_hash`; если он не изменился, эти поля не перезаписываются, обновляется только `last_processed_at`. Метрики (оценки, счётчики отзывов) в хэш не входят и сохраняются в историю при каждом обходе;
- для набора текстов отзывов хранится отдельный хэш; резюме пересчитывается через LLM только при его изменении.

## Конвейеры

Логика лежит в `backend/app/services/`: `crawl.py` (`run_crawl`), `analysis.py` (`run_analysis`), общая блокировка и имена конвейеров в `pipelines.py`. Их вызывают планировщик (`trigger = "schedule"`) и кнопки принудительного запуска (`trigger = "manual"`). Оба принимают источник параметром (`GameSource`), поэтому тестируются на заглушке без сети.

### Обход (`run_crawl`)

1. Если обход уже выполняется, новый не стартует: выбрасывается `PipelineRunning`.
2. Создаётся запись `sync_runs` (`pipeline = crawl`) со статусом `running`; она сразу фиксируется в БД.
3. `source.discover` возвращает самые новые игры; из них новыми считаются те, которых нет в базе. Из базы берутся игры с наступившим сроком `next_check_at`.
4. По лимиту выбирается, какие игры обработать (см. «Обход: открытие и повторные визиты»).
5. Для каждой игры: `source.fetch_game` по её идентификатору (сеть, без открытой транзакции), затем `save_game` в короткой транзакции, постановка срока следующей проверки и обновление счётчиков запуска. Ошибка одной игры логируется и учитывается в `games_failed`.
6. Запись `sync_runs` закрывается со статусом `success` или `failed`, временем окончания и итоговыми счётчиками.

Обход не использует модель и не зависит от ключа `LLM_API_KEY`.

### Анализ (`run_analysis`)

1. Если ключ модели не задан, конвейер выключен: запуск не создаёт записей (в статусе мониторинга видно «ИИ не настроен»), кнопка отвечает отказом.
2. Если анализ уже выполняется, новый не стартует (`PipelineRunning`).
3. Создаётся запись `sync_runs` (`pipeline = analysis`) со статусом `running`.
4. **Очередь выбирается по данным БД, без запросов к сайту** (см. «Шаг 3»): для каждой игры и типа отзывов берётся число отзывов из последней записи `game_overall_scores` и состояние `analysis_state`. Игра попадает в очередь, если у неё от 3 отзывов данного типа и либо её ещё не анализировали, либо число отзывов изменилось, а с прошлой проверки прошло не меньше суток. Кроме того, в очередь попадает тип отзывов, резюме которого построено более ранней версией запроса (см. «Запрос к модели»). Первыми идут игры, которых ещё не анализировали (самые новые), затем с устаревшей версией запроса, затем с самой старой проверкой. Берётся не больше `ANALYSIS_BUDGET` игр.
5. Для каждой игры: загружаются отзывы нужных типов (`source.fetch_reviews`), строится выборка, при изменении выборки (или устаревшей версии запроса) вызывается модель, резюме сохраняется. Ошибка одной игры логируется и учитывается в `games_failed`.
6. Запись `sync_runs` закрывается со статусом `success` или `failed` и счётчиками (`games_found` — сколько игр выбрано, `games_processed` — для скольких проверка завершилась, `games_failed` — сколько упало). Для каждой игры в `run_games` пишется строка с итогом: `summarized` (построено хотя бы одно резюме), `checked` (проверено, нового резюме не нужно), `retry` (модель была недоступна, игра останется в очереди) или `failed` (с текстом ошибки); в подробностях по каждому типу отзывов: `created` (резюме построено), `same_sample` (выборка прежняя), `too_few` (в выборке мало отзывов), `model_unavailable`, `bad_answer` (модель ответила неразборчиво).

## Работа с БД

Доступ к SQLite выполняется через SQLAlchemy 2.0 (синхронный ORM). Код лежит в `backend/app/db/`.

- `models.py` — ORM-модели, повторяющие [DATABASE.md](DATABASE.md): `Game`, `Genre`, `GamePlatform`, `GamePlatformHistory`, `ReviewSummary`, `SyncRun` и таблица связи `game_genres`.
- `session.py` — движок и сессии. На каждое соединение включаются `PRAGMA foreign_keys = ON` и `journal_mode = WAL`. `init_db()` применяет миграции Alembic при старте (`upgrade head`); если в базе уже есть таблицы, созданные до Alembic, ей ставится метка базовой миграции `0001` (она описывает схему на момент первого деплоя), после чего применяются остальные. `session_scope()` — одна сессия на операцию: `commit` при успехе, `rollback` при ошибке. Сессии между потоками не передаются: цикл (`asyncio.to_thread`) и API работают каждый со своей сессией; WAL позволяет читать во время записи.
- `repository.py` — функции доступа к данным; сложные запросы собраны здесь, а не размазаны по коду:
  - `save_game(session, source, game, now)` — создаёт или обновляет игру целиком (описательные поля, жанры, платформы). Считает `content_hash` по описательным полям и жанрам; если хэш не изменился, описательные поля не трогает и обновляет только `last_processed_at`. Метрики по платформам всегда обновляет в `game_platforms` и добавляет строкой в `game_platform_history`.
  - `processed_since(session, source, since)` — слаги игр, обработанных не раньше `since`.
  - Запросы на чтение для API игр лежат отдельно в `db/queries.py`: `list_games`, `get_game`, `list_platforms`, `similar_games`.
  - `start_run`, `update_progress`, `finish_run`, `count_successful_runs(session, source, since)` — журнал `sync_runs`; запись запуска адресуется по `id`, чтобы работать из разных сессий.
- `overall` (общие оценки) сохраняются в `save_game`: при каждой обработке игры в `game_overall_scores` добавляется строка для критиков и для игроков.
- `review_repository.py` — отзывы и резюме: `due_kinds` (какие резюме пора обновить), `latest_summary` и `latest_summaries`, `save_summary` (сохраняет отзывы выборки, пересиспользуя уже известные, версию резюме, пункты и связи пунктов с отзывами).
- Одна игра сохраняется в одной транзакции.
- Время хранится как наивный `datetime` в UTC.

## HTTP API

Роутеры лежат в `backend/app/api/`, схемы ответов — Pydantic-модели в `api/schemas.py`. Все пути начинаются с `/api`. Автодокументация FastAPI доступна на `/docs`.

Конвейеры и мониторинг (`/api/sync`):

| Метод и путь | Назначение |
|---|---|
| `GET /api/sync/status` | Состояние обоих конвейеров, ключи `crawl` и `analysis`: идёт ли запуск, интервал, лимит, время следующего запуска, текущий и последний запуск; у `analysis` ещё `enabled` (задан ли ключ модели) |
| `POST /api/sync/run?pipeline=crawl\|analysis` | Принудительный запуск конвейера. Ответ `202`; если он уже идёт — `409`; анализ без ключа модели — `400`. Запуск выполняется в фоне |
| `GET /api/sync/runs?pipeline=&limit=` | Журнал запусков, новые сверху (счётчики обновляются по ходу запуска); `pipeline` необязателен |
| `GET /api/sync/runs/{id}/games` | Игры, обработанные в запуске: название, ссылка на карточку (если игра есть в базе), итог, подробности, ошибка. Для запуска, сделанного до появления журнала игр, список пуст |

Игры (`/api/games`):

| Метод и путь | Назначение |
|---|---|
| `GET /api/games` | Список игр: `q` (поиск по названию), `platform` (слаг платформы), `sort` (`metascore`, `userscore`, `release`, `title`, `updated`), `order` (`asc`/`desc`), `page`, `page_size`. Ответ: `items`, `total`, `page`, `page_size` |
| `GET /api/games/platforms` | Платформы для фильтра: слаг, название, число игр |
| `GET /api/games/{id}` | Карточка игры: все поля (включая дату релиза), платформы с оценками, жанры, похожие игры |
| `GET /api/dashboard` | Данные дашборда главной страницы одним запросом (см. «Дашборд») |

Правила:
- Элемент списка — краткая информация: название, обложка, разработчик, жанры, платформы и **единая оценка игры** (поле `score`: `critics` и `users`).
- **Единая оценка игры** — среднее арифметическое оценок по платформам, у которых оценка есть: Metascore критиков (округляется до целого) и Userscore игроков (до десятых), отдельно. Она есть у любой игры, у которой есть хотя бы одна оценка на платформе, и не зависит от того, были ли собраны общие оценки со страницы Metacritic. Если задан фильтр `platform`, считается только по этой платформе. Игра без оценок получает `null`.
- Сортировка `release` идёт по дате релиза, новые первыми; игры без даты и с датой в будущем в конце.
- Сортировка по рейтингу (`metascore`, `userscore`) идёт по этой же единой оценке, поэтому порядок в списке совпадает с оценкой на карточках. Игры без оценки всегда в конце. По умолчанию: `metascore`, `desc`.
- **Похожие игры** вычисляются на лету из игр, уже имеющихся в базе: мера сходства — коэффициент Жаккара по жанрам плюс небольшой бонус за общие платформы; при равенстве выше игра с большим Metascore. В карточке показываются 6 лучших. Игра без жанров похожих не имеет.
- В карточке есть общие оценки критиков и игроков (поле `overall`, ключи `critics` и `users`, см. ниже) и резюме по отзывам (поле `summaries`, см. «Шаг 3»).
- **Общие оценки** (`overall`) — это то, что Metacritic показывает в шапке страницы игры: оценка, вердикт, число отзывов и распределение положительных, смешанных и отрицательных (для платформы, которую страница показывает по умолчанию; у игры с одной платформой это её оценки). Берётся самая свежая запись; если оценки нет (например, у игроков «Available after 4 ratings»), оценка и вердикт пустые. Оценки по платформам остаются отдельно в `platforms`.

## Дашборд

Главная страница (`/`) отвечает на вопрос «какие игры успешнее и почему». Это анализ рынка по играм, которые собрал обход, а не показатели работы сервиса (они на странице мониторинга). Все цифры приходят одним запросом `GET /api/dashboard`; агрегаты считаются SQL-запросами в `db/queries.py`.

**Что считается успехом.** Единого индекса нет, чтобы не прятать, из чего сложилось число. Игра описывается двумя осями:
- **качество** — единая оценка игры (среднее по платформам): Metascore критиков и Userscore игроков;
- **внимание** — число оценок игроков, суммарно по платформам. Это косвенный признак размера аудитории: он зависит от платформы и бывает искажён «бомбёжкой» отзывов.

**Дата релиза.** Для трендов рынка нужна дата выхода игры, а не дата попадания в нашу базу. Её даёт страница игры (`datePublished` в JSON-LD). Дата сохраняется в `games.release_date` при каждом посещении игры; у игр, обработанных до появления поля, она появится при следующем визите.

Блоки (ответ `/api/dashboard`):

| Блок | Поля ответа | Как считается |
|---|---|---|
| **Плитки** `tiles` | `games_total`, `new_7d`, `hits_share`, `avg_gap` | всего игр; игр, впервые попавших в базу за 7 дней; доля «хитов» среди игр, у которых есть обе оценки (критики от 75 и игроки от 7,5), в процентах; средний разрыв критиков и игроков `abs(Metascore - Userscore × 10)` по тем же играм |
| **Карта успеха** `map` | `points` (`id`, `title`, `critics`, `users`, `attention`), `attention_median` | точка на каждую игру, у которой есть внимание (больше нуля оценок игроков) и хотя бы одна оценка; оси: внимание (логарифмическая шкала) и оценка (переключатель «критики / игроки»); пороги зон: оценка 75 (игроки 7,5) и медиана внимания |
| **Жанры** `genres` | `genre`, `games`, `avg_critics`, `avg_users`, `avg_attention` | жанры, в которых не меньше 3 игр, 10 самых частых; средние берутся по единым оценкам игр и по их суммарному вниманию |
| **Расхождения** `divergences` | `critics_love`, `players_love`: по 5 игр (`id`, `title`, `critics`, `users`, `gap`, `reason`) | игры с обеими оценками и не меньше 10 оценок игроков; `gap = Metascore - Userscore × 10`: самый большой положительный («критики хвалят, игроки ругают») и самый большой отрицательный («игроки любят, критики ругают»); `reason` — главный пункт «что не нравится» из резюме ИИ той стороны, которая недовольна (у первой группы резюме игроков, у второй резюме критиков); `null`, если резюме ещё нет |
| **Ритм рынка** `rhythm` | `days` (`date`, `games`, `avg_critics`, `games_avg7`, `critics_avg7`), `coverage` (`with_date`, `total`) | последние 30 дней по дате релиза, дни без релизов с нулём; `games_avg7` — среднее число релизов в день за скользящие 7 дней, `critics_avg7` — средний Metascore игр, вышедших за эти 7 дней; игры без даты и с датой в будущем не учитываются, `coverage` показывает, у какой доли игр дата известна |

Блоки, которым нужна накопленная история (рост числа оценок за неделю, изменение оценок за неделю) и разметка причин в резюме по категориям, появятся позже, когда наберутся данные; структура страницы это допускает.

## Frontend

Стек: React, TypeScript, Vite, Tailwind CSS и shadcn/ui (компоненты копируются в репозиторий в `src/components/ui`). Данные запрашиваются через TanStack Query: он же даёт периодический опрос для мониторинга. Маршрутизация — React Router.

```
frontend/
├── src/
│   ├── api/          # типы и функции запросов к /api
│   ├── components/   # общие компоненты; ui/ — shadcn
│   ├── pages/        # DashboardPage, GamesPage, GamePage, MonitoringPage
│   ├── lib/          # утилиты
│   ├── App.tsx       # маршруты и общий каркас
│   └── main.tsx
├── vite.config.ts    # dev-прокси /api -> http://localhost:8000
└── package.json
```

Экраны:
- **Главная** (`/`): дашборд (плитки, карта успеха, жанры, расхождения критиков и игроков, ритм рынка; см. «Дашборд») и под ним карусель «Недавние релизы» (12 игр по дате релиза) с кнопкой «Смотреть все», которая открывает полный список `/games`. Карта успеха квадратная, справа от неё на оставшейся ширине таблица жанров (на узких экранах блоки идут друг под другом). Графики рисует Recharts; оценки в них окрашены по шкале Metacritic (зелёный, жёлтый, красный), остальное одним нейтральным цветом.
- **Игры** (`/games`): сетка карточек с обложкой, перечнем платформ и одной единой оценкой игры (критики в квадрате, игроки в круге); поиск по названию, фильтр по платформе, сортировка по рейтингу, постраничная навигация.
- **Карточка игры** (`/games/:id`), сверху вниз:
  1. **Шапка.** Слева слайдер «обложка и трейлер» (см. ниже), справа название, разработчик, дата выхода, жанры и описание, а по правому краю шапки, напротив названия, единая оценка игры (та же, что на карточке в списке: Metascore в квадрате и Userscore в круге). Общие оценки Metacritic с вердиктом и распределением показываются в блоке отзывов. Описание по умолчанию свёрнуто до нижней границы обложки (правая колонка не выше картинки) с затуханием и кнопкой «Показать полностью» / «Свернуть»; кнопка есть, только если текст не помещается. На узких экранах описание ограничено несколькими строками.
  2. Под шапкой: время обновления и ссылка на страницу игры на Metacritic. Отдельного раздела с трейлером нет: он лежит в слайдере.
  3. **Оценки по платформам** карточками: название платформы, Metascore в скруглённом квадрате и число отзывов критиков, Userscore в круге и число оценок игроков.
  4. **Отзывы.** Две вкладки: «Отзывы критиков» и «Отзывы игроков» (в подписи число отзывов). Внутри вкладки сверху оценка в стиле Metacritic: оценка (критики в квадрате, игроки в круге), вердикт, «На основе N отзывов» и полоса распределения положительных, смешанных и отрицательных с числами. Ниже две части рядом (на узких экранах одна под другой):
     - **слева резюме ИИ**: подпись о размере выборки («По 40 из 1405 отзывов», модель, время; у критиков пометка о смещении выборки к высоким оценкам) и два раздела, «Что нравится» (**зелёный**, значок «палец вверх») и «Что не нравится» (**красный**, значок «палец вниз»); пункты на английском, как и отзывы, у каждого пункта число отзывов; цвет не единственный признак: разделы различаются заголовком и значком;
     - **справа сами отзывы** выборки, на которой построено резюме: над списком переключатель тональности (Все, Положительные, Смешанные, Отрицательные) и список отзывов (автор, оценка, дата, платформа, текст, ссылка на полный обзор у критиков).
     **Клик по пункту слева фильтрует отзывы справа**: остаются только отзывы, на которых основан пункт (переключатель тональности при этом становится «Все»); у таких отзывов полоса слева цвета пункта (зелёная или красная), над списком метка фильтра того же цвета с кнопкой сброса. Повторный клик по тому же пункту или кнопка сброса снимает фильтр; переключатель тональности дополнительно сужает отфильтрованный список. Состояние (выбранный пункт и тональность) у каждой вкладки своё и сохраняется при переключении между вкладками. Если резюме для типа отзывов нет, вкладка показывает только оценку и пометку «Резюме ИИ и отзывы пока недоступны».
  5. **Похожие игры** каруселью: горизонтальная лента карточек со стрелками и прокруткой жестом; клик по карточке открывает игру.
  **Слайдер «обложка и трейлер».** Первый слайд — обложка, второй (если у игры есть видео) — трейлер; листается жестом (прокрутка пальцем или колесом по горизонтали), стрелками и точками. Слайдер занимает место обложки, высота шапки от него не меняется (описание сворачивается по-прежнему до нижней границы слайдера). Плеер подгружается, только когда слайд с трейлером показан, и выгружается при возвращении к обложке, поэтому видео не играет за кадром. Видео без встраиваемого плеера показывается ссылкой «Смотреть видео» на слайде.
  Канон оформления: оценки критиков везде в скруглённых квадратах, оценки игроков везде в кругах (также в списке игр); цвет по шкале Metacritic.
- **Мониторинг** (`/monitoring`): два блока, «Обход» и «Анализ отзывов». В каждом: идёт ли запуск, время следующего, лимит за запуск, кнопка принудительного запуска и таблица последних запусков конвейера с прогрессом; клик по строке запуска раскрывает список обработанных в нём игр: название (ссылка на карточку), итог и подробности (по ходу запуска список пополняется); у анализа пометка «ИИ не настроен», если нет ключа модели; данные обновляются опросом каждые 2 секунды, пока идёт цикл, и реже в остальное время.

В режиме разработки фронтенд обращается к `/api` через прокси Vite, поэтому CORS не нужен. Публикация собранного фронтенда описана в разделе «Деплой».

## Деплой

Сервис работает на одном VPS (HostVDS, Ubuntu 24.04) в Docker Compose. SQLite требует ровно один экземпляр бэкенда, поэтому масштабирование и несколько воркеров не используются.

```
Интернет ──► :80/:443  Caddy (контейнер web) ─┬─► статика фронтенда (/srv)
                                              └─► /api/* ─► backend:8000 (uvicorn) ─► том /data (SQLite)
```

- **backend** — образ из `backend/Dockerfile` (Python 3.12, запуск не от root). База лежит в именованном томе `/data` и переживает обновления. Порт наружу не публикуется.
- **web** — образ из `frontend/Dockerfile`: сборка фронтенда в Node и раздача результата через Caddy. Caddy проксирует `/api` на бэкенд. Адрес сайта задаётся переменной `SITE_ADDRESS`: по умолчанию `:80` (доступ по IP по HTTP); для HTTPS достаточно указать домен, сертификат Caddy получит сам.
- `docker-compose.yml` в корне описывает оба сервиса. У каждого есть и `build` (локальная сборка), и `image` из GitHub Container Registry (`ghcr.io/budum-tss/...`, имена в нижнем регистре).

### Сервер

Один раз вручную: Docker, firewall `ufw` (порты 22, 80, 443), пользователь `deploy` в группе `docker` с входом только по SSH-ключу. Каталог приложения — `~/app`. Файл `~/app/.env` создаётся деплоем из секретов GitHub (права `600`) и перезаписывается при каждом деплое: править его на сервере вручную не нужно.

### GitHub Actions

- `ci.yml` — проверки: тесты бэкенда (`pytest`), линтер и сборка фронтенда. Запускается на pull request, на push в ветки кроме `main` и вызывается из деплоя.
- `deploy.yml` — на push в `main` (и вручную): 1) вызывает `ci.yml`; 2) собирает оба образа и отправляет в GHCR с тегами `latest` и коммита; 3) по SSH копирует `docker-compose.yml` на сервер, входит в GHCR временным токеном запуска, выполняет `docker compose pull` и `up -d`, удаляет старые образы. Одновременно выполняется только один деплой.

Секреты репозитория: `SSH_HOST`, `SSH_USER`, `SSH_KEY` (приватный ключ, отдельный для деплоя) и `LLM_API_KEY` (ключ API языковой модели для резюме отзывов). Переменные репозитория (все необязательные): `LLM_BASE_URL` (адрес API), `LLM_MODEL` (имя модели) и `SITE_ADDRESS` (домен для HTTPS). Токены для GHCR хранить не нужно: используется `GITHUB_TOKEN`.

Из секретов и переменных деплой собирает `~/app/.env` на сервере; его подхватывают `docker-compose.yml` (подстановка `SITE_ADDRESS`) и бэкенд (`env_file`). Несекретные значения хранятся в переменных, а не в секретах, чтобы их было видно и можно было менять без правки кода. Если переменная не задана, берётся значение по умолчанию из настроек бэкенда: `https://ai.starimg.ru` и `claude-haiku-5-5`.

## Шаг 1. Парсер списка игр (Metacritic)

Задача: находить новые игры. Список используется только для открытия (`MetacriticSource.discover`), повторные визиты идут по ссылке игры (см. «Открытие и повторные визиты»).

Источники, в порядке просмотра:

1. Страница Games https://www.metacritic.com/game/, раздел **New Releases** (20 игр).
2. Раздел **SEE ALL** (сортировка «Новые»): https://www.metacritic.com/browse/game/all/all/all-time/new/, страница за страницей, пока не набрано нужное число игр или очередная страница не перестала давать новые.

Результат: идентификаторы игр, самые новые первыми, без повторов (игра из New Releases, встреченная и в SEE ALL, считается один раз).

### Откуда берутся данные (Metacritic, проверено на живых страницах)

Страницы отдаются сервером в виде готового HTML (Nuxt SSR), выполнять JavaScript не нужно, достаточно `requests` и BeautifulSoup. Обычный User-Agent браузера принимается, код ответа 200.

- **New Releases** (`/game/`): блок `data-testid="new-game-release-carousel"`, внутри 20 карточек `data-testid="product-card"`. Ссылка на игру — `a[data-testid="product-card-content"]`, `href` вида `/game/<slug>/`.
- **SEE ALL** (`/browse/game/all/all/all-time/new/`): карточки `data-testid="filter-results"`, внутри `a` с `href` `/game/<slug>/`. **На странице 50 игр**, страницы не пересекаются. Следующая страница — параметр `?page=N`.
- Из списков нужен только `slug`. Остальные данные берутся со страницы игры.


## Шаг 2. Парсер страницы игры (Metacritic)

Задача: по URL игры извлечь данные и сохранить их в БД.

Извлекаемые поля:

| Поле | Примечание |
|---|---|
| Название игры | |
| Картинка-обложка | URL изображения |
| Платформы | Для каждой платформы: Metascore и Userscore (платформ может быть много: ps5, ns2 и т.д.) |
| Разработчик | |
| Описание | |
| Ссылка на видео | |

Игра уже есть в базе — запись обновляется, иначе создаётся новая.

### Откуда берутся данные (Metacritic, проверено на живых страницах)

| Поле | Откуда берётся |
|---|---|
| Название | JSON-LD (`script[type="application/ld+json"]`, тип `VideoGame`), поле `name`; запасной вариант — `h1` в `data-testid="hero-title"` |
| Обложка | JSON-LD, поле `image` |
| Описание | JSON-LD, поле `description` |
| Видео | JSON-LD, `trailer.embedUrl` (страница плеера) и `trailer.contentUrl` (поток `.m3u8`); не у всех игр есть |
| Жанры | JSON-LD, поле `genre`; полный список — блок `data-testid="game-details"` |
| Разработчик | `data-testid="hero-summary-developer"`, ссылка внутри |
| Платформы и Metascore | блок `data-testid="all-platforms"`: карточки `data-testid="product-score-card"`; название платформы — атрибут `title` у иконки, слаг платформы — параметр `?platform=` в `href`, Metascore и число критических отзывов — текст карточки |
| Userscore и число пользовательских оценок | блок `data-testid="user-reviews"`; значение зависит от платформы и запрашивается страницей игры с `?platform=<слаг>` |
| Общие оценки игры (как на сайте) | блоки `data-testid="product-score"` (критики) и `data-testid="user-reviews"` (игроки) страницы игры: оценка (`global-score-value`), вердикт (`global-score-sentiment`, например «Generally Favorable»), число отзывов («Based on N …»), число положительных, смешанных и отрицательных отзывов (подписи вида «50 positive reviews (98%)») |

Замечания:
- Если у игры одна платформа, блока `all-platforms` с карточками может не быть: тогда платформа и оценка берутся из блока `platform-selector` и из основного блока оценки (`data-testid="product-score"`).
- Оценки может не быть (`tbd`). В базу тогда пишется `NULL`.
- Userscore по каждой платформе требует отдельного запроса `?platform=...`. Запросы идут последовательно, с паузой между ними.


## Шаг 3. Обработка отзывов

Для каждой игры строятся два резюме: по отзывам критиков и по отзывам пользователей, отдельно. Резюме содержит пункты «что нравится» и «что не нравится»; каждый пункт связан с отзывами, на которых он основан, чтобы по клику показать сами отзывы. Язык резюме и запросов к модели — английский, как и сами отзывы на Metacritic.

### Откуда берутся отзывы (только HTML-страницы, проверено на живых страницах)

Внутренний API сайта не используется: он не документирован, и ключ в его странице принадлежит самому фронтенду, а не нам. Параметры адреса (`sort`, `filter`) на HTML страниц отзывов не влияют: сервер всегда отдаёт один и тот же первый список.

| Источник | Что даёт |
|---|---|
| Блок отзывов на странице игры (`/game/<slug>/`, уже загружается) | около 7 отзывов критиков и около 7 пользователей с разнообразными оценками: у Metacritic это подборка разной тональности |
| `/game/<slug>/critic-reviews/?platform=<слаг>` | 10 отзывов критиков с самыми высокими оценками; берутся две платформы с наибольшим числом отзывов критиков |
| `/game/<slug>/user-reviews/?platform=<слаг>` | 50 последних отзывов пользователей; берётся платформа с наибольшим числом отзывов пользователей |

В отзыве: автор (издание или имя пользователя), оценка, дата, текст, у критиков ещё ссылка на полный обзор. Идентификатора на странице нет, поэтому ключ отзыва — `sha256` от `(тип, автор, дата, оценка, текст)`. Пользовательские отзывы со спойлерами пропускаются: в HTML вместо текста только строка «[SPOILER ALERT…]».

Сводная статистика берётся со страницы игры: общее число отзывов и распределение положительных, смешанных и отрицательных (с оценкой в процентах и числах).

**Ограничение:** отзывы критиков в выборке смещены к высоким оценкам (положительные заведомо преобладают). Это учитывается в запросе к модели и показывается пользователю подписью в карточке.

### Сборка выборки

1. Отзывы из всех источников объединяются, дубли убираются по ключу.
2. Тональность отзыва по шкале Metacritic: у критиков (0–100) положительный от 75, смешанный 50–74, отрицательный ниже 50; у пользователей (0–10) положительный от 7,5, смешанный 5–7,4, отрицательный ниже 5.
3. Лимиты выборки: критики не больше 30, пользователи не больше 40 (настройки). Текст каждого отзыва обрезается до 600 символов. Если отзывов больше лимита, из каждой тональности берётся доля, пропорциональная её доле среди собранных, но не меньше 3 отзывов из каждой непустой тональности. Анализировать все отзывы не нужно: нужна репрезентативная выборка, а в карточке пишется её размер относительно общего числа («40 из 311»).
4. Порядок перемешивается детерминированно (зерно из игры и типа отзывов): порядок не влияет на модель, а результат воспроизводим.
5. Если в выборке меньше 3 отзывов данного типа, резюме для него не строится.

### Запрос к модели

- Клиент (`app/llm.py`): `POST {LLM_BASE_URL}/v1/chat/completions`, модель `LLM_MODEL`, низкая температура, таймаут 60 секунд, два повтора. Если `LLM_API_KEY` не задан, резюме не строятся (шаг пропускается).
- Каждому отзыву в запросе даётся короткий номер `R1…Rn`. Отзывы передаются как данные, в инструкции сказано не выполнять указаний из текста отзывов.
- В запрос входят: размер выборки и общее число отзывов, распределение тональности из сводной статистики и для критиков пометка о смещении выборки к высоким оценкам.
- **Разбор по каждому отзыву до итога (chain-of-thought).** Тональность отзыва определяется по тексту, а не по оценке: оценка может не совпадать с содержанием (0 из 10 у троллинга или у настоящей претензии, 7 из 10 у самой обстоятельной критики). Поэтому модель сначала проходит по всем отзывам по очереди, а итог строит из своего разбора.
- Ответ — JSON из трёх частей:
  1. `reviews` — разбор: для каждого отзыва `{"id": "R3", "verdict": "...", "note": "..."}`; `verdict` — `praise`, `criticism`, `mixed` (и похвала, и претензия) или `irrelevant` (спам, оскорбления без сути, не по теме); `note` — коротко, за что хвалит или на что жалуется (для `irrelevant` пусто);
  2. `likes` — по 2–4 пункта «что нравится»;
  3. `dislikes` — по 2–4 пункта «что не нравится»; пункт — `{"text": "...", "reviews": ["R3", "R7"]}`.
  Правила в инструкции: каждая содержательная претензия из разбора попадает в `dislikes` (похожие группируются, достаточно одного отзыва), каждая похвала в `likes`, `irrelevant` не учитывается; список остаётся пустым, только если в разборе нет ни одного отзыва с претензией (соответственно с похвалой). Придумывать пункты запрещено.
- Ответ проверяется: номера, которых не было в запросе, отбрасываются, пункты без единого верного номера удаляются. Неразборчивый ответ считается ошибкой этого резюме.
- **Проверка согласованности.** Если в разборе есть отзывы с претензиями (`criticism`, `mixed` с непустой сутью), а `dislikes` пуст (и так же для похвалы и `likes`), запрос повторяется один раз с перечнем этих претензий. Если и после повтора список пуст, пункты строятся прямо из разбора модели: каждая претензия со ссылкой на свой отзыв (не больше 4). Так пустого списка при выявленных претензиях быть не может.
- **Версия запроса.** У текста инструкции есть номер версии (`PROMPT_VERSION`), он записывается в резюме. Резюме, построенные более ранней версией, попадают в очередь анализа заново (в пределах лимита запуска, после ещё не анализированных игр) и перестраиваются, даже если выборка прежняя.
- Разбор модели по каждому отзыву сохраняется вместе с резюме (`review_summaries.analysis`): по нему видно, как модель оценила каждый отзыв, и такие случаи можно разбирать по данным.

### Когда резюме пересчитывается и как не тратить токены

Анализ идёт отдельным конвейером (см. «Конвейеры»). Игры и типы отзывов в его очередь отбираются по данным БД, поэтому проверки до обращения к сайту и модели такие, от дешёвой к дорогой; на любой из них обработка данного типа останавливается:

1. **Есть ли отзывы.** Число отзывов берётся из `game_overall_scores` (его уже записал обход). Если их меньше 3, игра в очередь не попадает: ни запросов, ни токенов.
2. **Анализировали ли и менялось ли число.** Состояние хранится в `analysis_state` (игра, тип, когда проверяли, сколько было отзывов). Если игру уже проверяли и число отзывов не изменилось, она в очередь не попадает.
3. **Срок.** Повторная проверка при изменившемся числе отзывов не раньше чем через `SUMMARY_MIN_INTERVAL_HOURS` (24 часа): у популярных игр новые отзывы появляются почти каждый час.
4. **Страницы отзывов.** Только теперь загружаются страницы отзывов (только нужных типов) и строится выборка. Если `reviews_hash` выборки совпадает с хэшем прошлого резюме, модель не вызывается.
5. **Ответ модели.** Модель вызывается, только если все проверки пройдены.

После каждой завершённой проверки (нашлось резюме, выборка оказалась мала, выборка та же, модель ответила неразборчиво) в `analysis_state` записываются время и число отзывов: игра не вернётся в очередь, пока число отзывов не изменится. Исключение: если модель или сеть недоступны (`LLMError`), состояние не записывается, и игра будет проверена при следующем запуске.

### Хранение

Отзывы выборки сохраняются в БД: перезагрузить конкретный отзыв с сайта ненадёжно, а пользователь должен видеть тексты, на которых основан пункт. Хранится только выборка (не больше 70 отзывов на игру), строки не дублируются благодаря ключу. Таблицы `reviews`, `review_summaries`, `summary_reviews` (вся выборка резюме), `summary_points`, `summary_point_reviews` описаны в [DATABASE.md](DATABASE.md). Изменение схемы выполняет миграция Alembic.

### API и интерфейс

- `GET /api/games/{id}` получает поле `summaries` с ключами `critics` и `users` (или `null`, если резюме нет). Резюме содержит: `generated_at`, `sample_size`, `total_reviews`, `model`, пункты `likes` и `dislikes` (у каждого `id`, `text`, `review_ids`) и список `reviews` (`id`, автор, оценка, дата, платформа, текст, ссылка): вся выборка, на которой построено резюме; пункты ссылаются на неё по `id`. Отдельного эндпоинта для отзывов нет.
- Карточка игры: блок отзывов описан в разделе «Frontend» (резюме ИИ в две колонки, клик по пункту фильтрует отзывы).

## Хранилище

Используется SQLite. Сохраняются только отзывы, вошедшие в выборку для резюме (не больше 70 на игру), вместе с резюме и хэшем выборки.

Данные для анализа версионируются: метрики и резюме не перезаписываются, а накапливаются по времени, чтобы строить графики. Время хранится в UTC.

Полное описание таблиц, полей и индексов — в [DATABASE.md](DATABASE.md).
