# Архитектура

Документ описывает решение по мере его проектирования. Постановка задачи: [TASK.md](../TASK.md).

## Стек

| Назначение | Выбор |
|---|---|
| Парсинг HTML | BeautifulSoup (`beautifulsoup4`) |
| HTTP-клиент | `requests` (синхронный) |
| Хранилище | SQLite |
| Бэкенд и веб-интерфейс | FastAPI + uvicorn (один процесс) |
| Планировщик | APScheduler 3.x (`AsyncIOScheduler`), версия закрепляется как `>=3.10,<4` |

## Общая схема

```
Metacritic ──► Парсер списка игр ──► ссылки на игры
                                          │
                                          ▼
                              Парсер страницы игры ──► SQLite
                                                          ▲
                              Обработка отзывов (позже) ──┘
```

## Структура проекта

Репозиторий делится на две независимые части:

```
metacritic_dashboard/
├── backend/     # FastAPI, планировщик, парсеры, SQLite
│   ├── app/
│   │   ├── api/         # HTTP-эндпоинты
│   │   ├── parsers/     # парсеры списка игр и страницы игры
│   │   ├── db/          # подключение, схема, репозитории
│   │   ├── scheduler/   # APScheduler и run_cycle
│   │   └── main.py      # приложение FastAPI, lifespan
│   ├── tests/
│   ├── pyproject.toml   # зависимости и настройки
│   └── .env.example
├── frontend/    # веб-интерфейс (UI)
├── docs/
├── AGENTS.md
├── CHANGELOG.md
└── TASK.md
```

Фронтенд общается с бэкендом только через HTTP API. Зависимости, конфигурация и тесты бэкенда лежат внутри `backend/`.

## Запуск по расписанию

Обработка запускается раз в час планировщиком, встроенным в приложение FastAPI. Внешний cron и брокер не нужны.

- `AsyncIOScheduler` создаётся и запускается в `lifespan` FastAPI и останавливается при завершении приложения.
- Задача `run_cycle` регистрируется с интервалом 1 час и `max_instances=1`: новый цикл не стартует, пока идёт предыдущий.
- Парсинг синхронный (`requests` + BeautifulSoup), поэтому внутри задачи он вызывается через `asyncio.to_thread`, чтобы не блокировать API.
- Принудительный запуск (кнопка в интерфейсе) вызывает ту же `run_cycle`. Защита от параллельного запуска общая: флаг «цикл выполняется» плюс `max_instances=1`.
- Приложение запускается одним процессом uvicorn (без `--workers N`), иначе у каждого воркера появится свой планировщик.

### Выбор пачки игр за запуск

За один запуск обрабатывается ровно 20 игр (размер пачки — настройка `BATCH_SIZE`). Отдельной таблицы состояния нет: следующая пачка выводится из журнала запусков `sync_runs` (последний успешный запуск за сегодня).

1. Если сегодня успешных запусков ещё не было, берём 20 игр из New Releases (`source = new_releases`).
2. Иначе берём пачку из SEE ALL (`source = see_all`) со сдвигом `offset`: для первого запуска SEE ALL `offset = 0`, далее `offset` предыдущего успешного запуска SEE ALL плюс размер пачки.
3. Страница SEE ALL содержит 50 игр, поэтому пачка вычисляется из сдвига: номер страницы `offset // 50 + 1`, начало среза `offset % 50`. Если пачка выходит за границу страницы, дозагружается следующая (`?page=N+1`).
4. Игры, уже обработанные сегодня (`last_processed_at`), пропускаются.

Границы дня считаются по UTC. Запись в `sync_runs` получает статус `success` только после обработки всей пачки, поэтому при сбое посреди цикла следующий запуск повторит ту же пачку.

### Обнаружение изменений

Хэш всей HTML-страницы не используется: в ней много динамического шума, а скачивать страницу всё равно приходится. Вместо этого:

- по описательным полям игры (название, обложка, разработчик, описание, видео, жанры; нормализованный отсортированный JSON) считается `games.content_hash`; если он не изменился, эти поля не перезаписываются, обновляется только `last_processed_at`. Метрики (оценки, счётчики отзывов) в хэш не входят и сохраняются в историю при каждом обходе;
- для набора текстов отзывов хранится отдельный хэш; резюме пересчитывается через LLM только при его изменении.

## Шаг 1. Парсер списка игр

Задача: получить список ссылок на игры (по 20 за запуск).

Источники:

1. **Первый запуск за день** — страница Games https://www.metacritic.com/game/, раздел **New Releases** (первые 20 игр).
2. **Последующие запуски** — раздел **SEE ALL** (сортировка «Новые»): https://www.metacritic.com/browse/game/all/all/all-time/new/. За каждый заход обрабатывается очередная страница списка.

Результат: список URL страниц игр, которые передаются парсеру страницы игры.

### Источники данных (проверено на живых страницах)

Страницы отдаются сервером в виде готового HTML (Nuxt SSR), выполнять JavaScript не нужно, достаточно `requests` и BeautifulSoup. Обычный User-Agent браузера принимается, код ответа 200.

- **New Releases** (`/game/`): блок `data-testid="new-game-release-carousel"`, внутри 20 карточек `data-testid="product-card"`. Ссылка на игру — `a[data-testid="product-card-content"]`, `href` вида `/game/<slug>/`.
- **SEE ALL** (`/browse/game/all/all/all-time/new/`): карточки `data-testid="filter-results"`, внутри `a` с `href` `/game/<slug>/`. **На странице 50 игр**, страницы не пересекаются. Следующая страница — параметр `?page=N`. Пачка в 20 игр вырезается из страниц по сдвигу (см. «Выбор пачки игр за запуск»).
- Из списков нужен только `slug`. Остальные данные берутся со страницы игры.


## Шаг 2. Парсер страницы игры

Задача: по URL игры извлечь данные и сохранить их в БД.

Извлекаемые поля:

| Поле | Примечание |
|---|---|
| Название игры | |
| Картинка-обложка | URL изображения |
| Платформы | Для каждой платформы: Metascore и Userscore (платформ может быть много: ps5, ns2 и т.д.) |
| Разработчик | |
| Описание | |
| Ссылка на видео | |

Игра уже есть в базе — запись обновляется, иначе создаётся новая.

### Источники данных (проверено на живых страницах)

| Поле | Откуда берётся |
|---|---|
| Название | JSON-LD (`script[type="application/ld+json"]`, тип `VideoGame`), поле `name`; запасной вариант — `h1` в `data-testid="hero-title"` |
| Обложка | JSON-LD, поле `image` |
| Описание | JSON-LD, поле `description` |
| Видео | JSON-LD, `trailer.embedUrl` (страница плеера) и `trailer.contentUrl` (поток `.m3u8`); не у всех игр есть |
| Жанры | JSON-LD, поле `genre`; полный список — блок `data-testid="game-details"` |
| Разработчик | `data-testid="hero-summary-developer"`, ссылка внутри |
| Платформы и Metascore | блок `data-testid="all-platforms"`: карточки `data-testid="product-score-card"`; название платформы — атрибут `title` у иконки, слаг платформы — параметр `?platform=` в `href`, Metascore и число критических отзывов — текст карточки |
| Userscore и число пользовательских оценок | блок `data-testid="user-reviews"`; значение зависит от платформы и запрашивается страницей игры с `?platform=<слаг>` |

Замечания:
- Если у игры одна платформа, блока `all-platforms` с карточками может не быть: тогда платформа и оценка берутся из блока `platform-selector` и из основного блока оценки (`data-testid="product-score"`).
- Оценки может не быть (`tbd`). В базу тогда пишется `NULL`.
- Userscore по каждой платформе требует отдельного запроса `?platform=...`. Запросы идут последовательно, с паузой между ними.


## Шаг 3. Обработка отзывов

Отдельный шаг, будет описан позже. Резюме по отзывам критиков и пользователей строится отдельно и может обновляться при повторных обходах.

## Хранилище

Используется SQLite. Сырые отзывы не хранятся: их можно восстановить с Metacritic, в базе остаются только резюме и хэш набора отзывов.

Данные для анализа версионируются: метрики и резюме не перезаписываются, а накапливаются по времени, чтобы строить графики. Время хранится в UTC.

Полное описание таблиц, полей и индексов — в [DATABASE.md](DATABASE.md).
